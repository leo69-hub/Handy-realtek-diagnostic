# Handy 0.9.8 — диагностика Realtek 0x80070057

## Статус

Это изменённые исходники, **не готовый Windows EXE/MSI**. Полная сборка и запуск
на Realtek не выполнены: в среде подготовки нет Rust/Cargo, Bun, MSVC C++ Build
Tools, Windows SDK, CMake и Vulkan SDK. Изменение остаётся экспериментальным,
исправление вашей ошибки не подтверждено. Rust-тесты добавлены, но не запускались.

Основа: официальный https://github.com/cjpais/Handy, тег `v0.9.8`, коммит
`14f6f0d31cb22a4268acfbddba3052820fd0a06e` (3 октября 2026). Версии в
package.json, Cargo.toml и tauri.conf.json — 0.9.8; Cargo.lock фиксирует CPAL 0.16.0.
Версия диагностического патча: 1.

## Что изменено

Оригинальный `AudioRecorder::get_preferred_config` выбирает формат с приоритетом
F32 > I16 > I32 при частоте устройства по умолчанию. Ваш журнал показывает
сбой создания потока F32 / 48000 Hz / 2 канала, затем повтор с теми же параметрами.

В Windows переменная `HANDY_MIC_CONFIG` управляет выбором:

| Режим | Поведение |
| --- | --- |
| `auto` (по умолчанию) | Сначала конфигурация устройства по умолчанию, затем объявленные CPAL варианты I16 на той же частоте. |
| `default` | Только `default_input_config()`, без перечисления остальных форматов. |
| `i16` | Только объявленные CPAL варианты I16 на частоте устройства по умолчанию. Если их нет, выдаёт явную ошибку. |
| `legacy` | Исходный выбор конфигурации из v0.9.8 для сравнения. |

В `auto`/`i16` сначала рассматривается исходное число каналов, затем другие
объявленные варианты. Одинаковые комбинации частоты, каналов и формата не
повторяются. После ошибки создания или запуска потока пробуется следующий
кандидат; при распознанном отказе в доступе перебор прекращается. Каждый неудачный
поток уничтожается перед следующей попыткой. После исчерпания кандидатов
существующий менеджер Handy может заново найти устройство и повторить открытие.

Журнал содержит режим, конфигурацию по умолчанию, перечисленные варианты,
параметры каждой попытки, её ошибку или успешный результат. Windows намеренно
не использует кеш конфигурации при повторном открытии: это добавляет время на
опрос устройства, но делает результаты сравнения воспроизводимыми. Обработка
аудио, преобразование I16 в f32 и ресемплинг в 16 kHz остаются исходными.

`default_input_config()` тоже может вернуть F32 / 48000 / 2. Тогда эта попытка
может совпасть с оригинальной и ничего не исправить. CPAL всё равно преобразует
свой конфиг в WASAPI-структуру; патч не передаёт необработанный WAVEFORMATEX из
GetMixFormat напрямую. Если I16 не перечислен, патч не навязывает драйверу
неподдерживаемый формат. Если все варианты дают тот же код, причина может быть
в другом параметре WASAPI или драйвере; это не доказательство дефекта F32.

Уже существует похожий отчёт с другим микрофоном:
https://github.com/cjpais/Handy/issues/990 — он не подтверждает причину на Realtek.

## Получение Windows x64 сборки через GitHub Actions

В архиве исходников уже лежит `.github/workflows/realtek-diagnostic.yml`.
Он использует официальный многошаговый build.yml из тега v0.9.8: установку
Vulkan SDK, SPIRV-Headers, ONNX Runtime, упаковку runtime DLL и проверку
содержимого установщиков. Подпись разработчика и артефакты автообновления
отключены отдельным конфигом. Имя приложения — Handy Realtek Diagnostic,
идентификатор — com.pais.handy.realtek-diagnostic, чтобы отделить настройки
от обычной установки. Это экспериментальная локальная модификация, не
официальный релиз Handy. Код workflow подготовлен, но удалённая сборка не запускалась.

1. Создайте свой fork официального репозитория и ветку от `v0.9.8`.
2. Примените приложенный патч в корне чистого checkout:

   ```powershell
   git switch -c realtek-diagnostic v0.9.8
   git apply --check C:\path\handy-0.9.8-realtek-diagnostic.patch
   git apply C:\path\handy-0.9.8-realtek-diagnostic.patch
   git add src-tauri/src/audio_toolkit/audio/recorder.rs src-tauri/src/audio_toolkit/audio/input_config.rs src-tauri/tauri.realtek-diagnostic.conf.json .github/workflows/realtek-diagnostic.yml diagnostic
   git commit -m "fix: diagnose Windows microphone format failures"
   git push -u origin realtek-diagnostic
   ```

3. В своём fork включите Actions. Если новый workflow не виден, добавьте его
   также в default-ветку fork (без изменения исходников базового тега).
4. Откройте Actions → Realtek diagnostic Windows x64 → Run workflow и выберите
   ветку realtek-diagnostic. Никакие секреты для подписи не нужны.
5. После **успешного** завершения скачайте artifact
   `handy-realtek-diagnostic-x86_64-pc-windows-msvc`.
   Он должен содержать установщики `.exe` (NSIS) и `.msi`.
   Не считайте workflow успешным, если он завершился ошибкой проверки DLL.

Этот процесс не выполнялся от вашего имени: репозиторий, PR и релиз не публиковались.
Удалённый workflow может потребовать корректировок при изменении внешних сервисов.

## Локальная сборка на подготовленном Windows x64

Следуйте BUILD.md: Rust stable, Bun, VS 2022 C++ Build Tools с Windows SDK,
CMake, Vulkan SDK. Откройте новую консоль после установки инструментов.

```powershell
bun install --frozen-lockfile
New-Item -ItemType Directory -Force src-tauri/resources/models
Invoke-WebRequest https://blob.handy.computer/silero_vad_v4.onnx -OutFile src-tauri/resources/models/silero_vad_v4.onnx
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib input_config::tests
bun run tauri build --config src-tauri/tauri.realtek-diagnostic.conf.json
```

Для распространяемого установщика воспроизведите также Windows x64 шаги
официального `.github/workflows/build.yml`: ORT_LIB_LOCATION,
ORT_PREFER_DYNAMIC_LINK, HANDY_VC_REDIST_DIRS и настройку SPIRV-Headers.
Простая команда выше не заменяет подготовку нативных зависимостей и DLL.
Рекомендуемый полный рецепт — приложенный Actions workflow.
Установщики после успешной локальной сборки находятся в
`src-tauri/target/release/bundle/nsis/` и `bundle/msi/`.
Не переносите один handy.exe без ресурсов и runtime DLL.

## Проверка микрофона после получения сборки

1. Полностью закройте обычный Handy через меню значка в трее. Сделайте копию
   его настроек при необходимости. Диагностическую версию установите отдельно;
   предпочтителен NSIS с выбором portable-режима в новую папку.
2. Не используйте старую папку Data для чистого сравнения. В portable-режиме
   программа создаст свою Data рядом с EXE. Выберите тот же модельный движок
   и микрофон «Микрофон (Realtek(R) Audio)»; при необходимости загрузите модель.
3. Запустите по очереди `legacy`, `default`, `i16`, `auto`. Между режимами
   полностью выходите через трей, чтобы новая переменная попала в новый процесс:

   ```powershell
   .\diagnostic\Start-Diagnostic.ps1 -Executable 'C:\path\Handy-Diagnostic\handy.exe' -Mode legacy
   ```

   Повторите команду с `-Mode default`, `-Mode i16`, `-Mode auto`.
   Скрипт не завершает работающие процессы; при открытом Handy попросит закрыть его.
   Если политика PowerShell блокирует скрипт, выполните эквивалент вручную:

   ```powershell
   $env:HANDY_MIC_CONFIG = 'i16'
   $env:HANDY_DISABLE_UPDATER = '1'
   & 'C:\path\Handy-Diagnostic\handy.exe' --debug
   ```

4. В каждом режиме включите подробное логирование (Debug/Trace, если нужно
   через Ctrl+Shift+D), запишите 5–10 секунд речи трижды и проверьте текст.
   Успешный `build/play` сам по себе не доказывает, что поступают аудиосэмплы:
   проверьте индикатор уровня, фактическую расшифровку и строки `first audio samples`
   / `first captured samples` в журнале. Затем проверьте повторный старт/стоп,
   режим on-demand и, если используете, always-on, а также смену/переподключение устройства.
5. Сохраните отдельный журнал для каждого режима. Portable-журналы находятся
   в `Data\logs` рядом с EXE; при обычной установке откройте папку журналов
   из приложения. Наличие строки `Realtek diagnostic patch v1` подтверждает,
   что запущен изменённый код.

Полезные данные: режим, устройство по умолчанию, объявленные форматы, параметры
и полный результат всех попыток, появляются ли первые сэмплы, слышна ли речь,
версия Windows и Realtek-драйвера. Перед передачей журнала проверьте его на
личные данные и распознанный текст.

Если legacy не работает, а I16 работает при тех же 48000 Hz / 2 каналах, это
сильный признак зависимости сбоя от конфигурации формата. Если default работает
при другом числе каналов или формате, сравните все параметры. Если `i16`
сообщает об отсутствии вариантов, это означает отсутствие объявленного I16
на текущей частоте, а не неудачный запуск I16-потока.

Для возврата закройте диагностическую версию и запустите обычный Handy.
При ручном запуске удалите переменные из своей консоли:

```powershell
Remove-Item Env:HANDY_MIC_CONFIG -ErrorAction SilentlyContinue
Remove-Item Env:HANDY_DISABLE_UPDATER -ErrorAction SilentlyContinue
```

## Проверки при подготовке

См. приложенный VALIDATION.txt: там разделены выполненные статические проверки
и невыполненные компиляция, Rust-тесты, установка и аппаратная проверка.
В патче есть шесть Rust-тестов планирования: порядок default/I16, сохранение
частоты, устранение дублей, I16 по умолчанию без перечисленных вариантов,
строгий отказ без I16 и проверка значения режима.
